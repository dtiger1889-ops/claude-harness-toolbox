# harness_me.txt — Claude Code harness installer

Audience: Claude Code or another file-capable coding agent.

Goal: install a durable, low-context workspace harness from this repository.

Use this file as an execution contract. Human-facing rationale, configuration guidance,
benchmark results, and component descriptions live in `README.md` and `docs/`; do not
load them during installation unless the user asks.

Last updated: 2026-11-14 (embedded workspace rulebook re-synced with the maintainer's
current rules: grouped sections, one live ask at a time, owner-gated todos, readiness and
coverage checks, no time estimates, file-edit-tools-only writes; embedded CHECKPOINT
template Pick line matches the repository template).

## 0. Hard rules

- Never delete or overwrite an existing file.
- Merge JSON; never replace an existing `~/.claude/settings.json`.
- Use the user's chosen workspace root everywhere. `~/Claude/` below is a placeholder.
- On Windows, the suggested root is `%USERPROFILE%\Documents\Claude\`. On Mac/Linux,
  the suggested root is `~/Claude/`.
- Hooks belong in the user-level `~/.claude/settings.json`, not the workspace-level file.
- Before each write, show the exact target path in Mode B or C.
- Record every created file in `<workspace>/HARNESS_files_created.md`.
- If a target exists, inspect it and propose a merge. Do not silently replace it.
- Prefer the repository's files over the embedded fallbacks in this guide.
- Use `CLAUDE.md` + `CHECKPOINT.md` as the durable store; do not add a second auto-memory store.

## 1. Collect inputs

Ask once for any unknown values:

1. Workspace root.
2. Operating system: Windows or Mac/Linux.
3. Install mode:
   - `A` — execute the approved install without phase pauses.
   - `B` — show the complete target manifest, wait for approval, then pause after each phase.
   - `C` — inspect the existing setup and request approval before each file or merge.
4. Snapshot: yes/no. Recommend yes when the workspace already contains files.
5. Components:
   - Core scaffold: workspace/project `CLAUDE.md` + `CHECKPOINT.md` templates.
   - Core hooks: SessionStart receipt + PreCompact reminder.
   - Recommended hooks: orientation gate; Windows mechanical guard.
   - Optional hooks: Windows security backstop; tmux/SSH environment receipt.
   - Optional Codex hooks (Windows PowerShell, only if Codex is installed): `hooks/codex/`.
   - Optional skills: named folders under `skills/`, or `all`.

If the user already supplied a value, do not ask again.

## 2. Preflight

1. Resolve the workspace root and repository root to absolute paths.
2. Inventory the workspace one level deep.
3. Detect existing:
   - workspace `CLAUDE.md` / `CHECKPOINT.md`;
   - per-project harness files;
   - `~/.claude/settings.json` and hook scripts;
   - `~/.claude/skills/` name collisions.
4. If snapshot=yes, write `<workspace>/BACKUP_snapshot_YYYY-MM-DD.md` with the inventory.
   This is an inventory, not a content backup.
5. Build the exact target manifest. In Mode B or C, wait for approval as defined above.

## 3. Install scaffold

Target layout:

- `<workspace>/CLAUDE.md`
- `<workspace>/CHECKPOINT.md`
- `<workspace>/_template/CLAUDE.md.template`
- `<workspace>/_template/CHECKPOINT.md.template`
- `<workspace>/.claude/settings.local.json`
- `<workspace>/HARNESS_files_created.md`
- per project: `<workspace>/<project>/CLAUDE.md` + `CHECKPOINT.md`

If this repository is available, copy the unfilled per-project templates from `templates/`.
Use the embedded templates below only when the repository files are unavailable. Replace
bracketed fields in live workspace/project files; keep the `_template` copies unfilled.

### Workspace CLAUDE.md

```markdown
# [USER'S NAME]'s Workspace
<!-- v1 — [DATE UTC] -->

This workspace holds [USER'S NAME]'s personal projects. Each immediate subfolder is a
project with its own `CLAUDE.md` (stable facts) and `CHECKPOINT.md` (mutable state).
This file is the project ledger and the shared rulebook all projects inherit.

## Startup sequence

0. **Orientation is enforced by the gate, not your own judgment.** Read-only work
   (Read/Grep/Glob, answering a lookup like "what does function Y do in Z.py") never trips
   the orientation gate, so a genuinely pre-oriented prompt pays zero ritual tax
   automatically — just answer it. But the first time you go to *change* a file, run a
   shell command, or hit the web, the PreToolUse orientation gate blocks it until this
   session has read the nearest CHECKPOINT.md in full — so do steps 1-3 first. Re-issuing
   the blocked call does not pass the repository gate (`hooks/orient_gate.ps1` / `.sh`);
   set `ORIENT_GATE_BLOCK_ONCE=1` to get the older block-once behaviour, where one re-issue
   lets a truly pre-oriented one-shot through. The embedded fallback in Section 8d is the
   simpler block-once form. (Why a gate instead of a self-judged "skip the ritual" rule: pre-oriented
   prompts cost a large token tax, so skipping when truly oriented matters — but a
   50-session audit found the model classifies "am I oriented?" unreliably and errs toward
   just acting. The gate makes read-only free and the action boundary mechanical.)
1. The SessionStart hook prints a CHECKPOINT *receipt* (file present + byte/line count),
   not the contents. Read CHECKPOINT.md to EOF before acting. If the Read shows a
   truncation or partial-view notice, re-Read until complete.
2. The CHECKPOINT "Next step" is a stale suggestion, not the agenda. The user's live ask
   and what you observe this session outrank it: don't steer back to it, defend it, or
   treat re-curating it as the deliverable. Don't silently abandon the open threads either.
3. If `Last updated:` is older than 30 days, verify or update CHECKPOINT before acting on
   what it claims (that line doubles as the "verified against reality" stamp).
4. Then act.

## Rules

### Files and state

- CLAUDE.md = stable facts only (≤30 lines, hard cap). Version stamp on line 2; bump it on
  a substantive change and log one line in that project's CHECKPOINT changelog.
  If it grows past 30, move surplus to `<project>/INVENTORY.md` and reference it.
- CHECKPOINT.md = mutable state (≤120 lines, ~30KB). Overwrite in place, never append.
  On overflow: archive oldest changelog entries to `archive/harness_changelog.md` first.
  Changelog entries are immutable history: never summarize, shorten, or retype them.
- Update CHECKPOINT.md at end of any logically complete task, and before /compact.
- Any hook/Read result showing "Output too large" or a partial-view notice is
  incomplete — Read the persisted file or re-Read the source to EOF before acting.
- No bare future-session promises. Before saying "I'll do X later/next session": either
  do it now, or write it into CHECKPOINT Open threads in the SAME turn and point at the
  thread. Litmus: "will the next session find this in a file it reads?"
- These harness files are the only durable memory. Don't keep the same facts in a second
  auto-memory store; if the two disagree, the harness files win.
- Don't re-read files already summarized in CHECKPOINT.md.
- Plans and specs written to disk are cold-start artifacts: written for a reader with no
  session context, with literal paths, commands, success criteria, and each pinned
  decision with who made it and when.
- Lean docs carry rules, not stories. In CLAUDE.md files, CHECKPOINT live sections, and
  script comments, a rule is trigger + directive + exceptions, then author, date, and a
  pointer to its changelog entry. Backstory and incident narrative go in the changelog.
- Rules for one kind of session (a scheduled run, an unattended loop, a helper agent) live
  in the skill, agent definition, or launch prompt that starts it, not as an unscoped
  imperative here: helper agents inherit this file.
- Fix a repeated session failure in the narrowest layer guaranteed to be read or fired at
  the failure point: a hook for a mechanical pattern, a skill for a procedure, a project
  CLAUDE.md for a stable fact, CHECKPOINT for mutable state, this file only for rules
  every session needs.
- Create and change files only with the file-edit tools (Write/Edit), never with a shell
  command that writes a file (`sed -i`, a heredoc, inline `python -c`, `Set-Content`).
  The shell runs commands and scripts saved with Write.
- Don't create README, status, or planning files unless asked.
- Move files with `mv`/`Move-Item`, then Edit in place — never Write-to-new-path +
  delete-old (orphan risk, history loss, double permission prompts).
- Research that pulls external data saves the raw responses, dated, to
  `<project>/archive/research_raw/` before analysis; the analysis links them.

### Serving the ask

- One live ask at a time. Serve the full live request (it may hold several related
  deliverables); don't silently switch to an unrelated open thread. A blocker stops only
  the directive it blocks: table that item in one line and keep working the rest in the
  same turn. A quoted ask beats your reframing of it: "read/review X" means read the
  existing X.
- An ask naming a collection that exists both per project and workspace-wide (open
  threads, the backlog, to-dos) gets ONE scope for all its clauses: a project it names
  anywhere; otherwise the folder the session opened in; workspace-wide only when it says
  so or the session runs at the workspace root. State the scope in the first plan line.
- "Add a todo: X" delivers the written entry. Never launch agents or implementation from it.
- On a correction: do the literal thing the user named first, name the failure in their
  words, and write no lesson until the diagnosis matches what they said.
- One statement is an instance, not a rule: record a standing rule only when the message
  carries rule words (from now on, always, never) or the user confirms.
- No unasked bulk work: a count-driven step states the count and cost, does one item,
  and leaves the rest unless the user asked for all.
- The folder probably already exists: before proposing a new folder or asking where
  something goes, check the Projects table and search the workspace for the topic.
- New project or new milestone: first turn produces a `## Research` block in
  CHECKPOINT.md (prior art, constraints, open questions, sources) before any
  implementation. Prior art means shipped solutions first (published repos, skills,
  write-ups); adopt or adapt with a citation, and greenfield needs a stated reason.
  Prune it into Key decisions once the milestone ships.
- Before building a generic component (data table, date picker, parser, scheduler, queue,
  auth, diff view), name the maintained library you checked and use it; hand-building
  needs a stated reason.

### Acting

- Just act — if a tool in this session can do the thing, DO it and report the outcome;
  don't end a turn *offering* to do work you could have just done. An offer is only worth
  it when the next step is genuinely expensive, irreversible, or a real fork the user must
  pick.
- A question is answered, not acted on: "why…?", "is that correct?", "what is Y?" never
  authorize editing, killing, or syncing anything. Act only if the answer surfaces a real
  problem, and say what you're doing and why. A decided rule or approved change that the
  answer shows was never applied IS that problem: apply it in the same turn.
- On a permission block, keep working: do everything the refusal doesn't block and try a
  permitted way to the same result. If only the user can unblock it, ask for that in one
  line; never hand them the edit to make.
- Owner-gated steps get tabled, not attempted. A step that structurally needs the user
  (sign-in, a physical device, a UI-only click, an account approval) becomes a complete
  todo: the exact link or file path, numbered steps with every value to type or pick, and
  what happens after; a todo with a choice puts the options and your recommendation
  before the steps. A todo asking them to create or enter a key or password names where
  to get it and where to store it, never the chat. One cheap probe to confirm the gate is
  fine; a retry ladder is not. A re-upload or restart at the END of your work never gates
  that work: do the work, then table the step.
- A decision is the user's only when the options differ in something they alone own
  (money, accounts, devices, data, taste, people, scope they set). A defect in the
  workspace's own tools, framed as a choice, is yours to diagnose, fix, and prepare.
- A request that matches an installed skill invokes the skill; don't read its SKILL.md
  "to understand it first". Loaded skill instructions are a procedure to run. Exception:
  for a "best practices" ask, research published examples and guidance online first and
  save the URLs; an installed skill is never the source of best practice.
- A step taken from an outside page (a vendor checklist, a guide) keeps the page's own
  word ("recommended", "optional") and its link, says the user did not ask for it, and
  waits for their yes; a go on the parent task does not cover it.
- Verify the why before changing stale-looking state: when files, paths, or configs look
  redundant or wrong, find out why they were set up that way before removing or
  refactoring them. Same bar for citing a rule as the reason not to do something: find
  what it protects and confirm that still holds.
- Never restart the agent, close its windows, end its sessions, or restart an app holding
  the user's active work without their explicit approval of that interruption. A request
  to fix or clean up is not that approval. Finish the non-disruptive work first, then ask.
- Temporary helper processes get a finite deadline with forced-stop escalation; afterwards
  end only the helpers this task started, checked by process ID and start time.
- Delegated work that ships is checked against the original brief, not the helper's
  summary. Size decides whether to delegate (a handful of commands runs inline);
  reasoning need decides which model. A big job is not a hard job.

### Claims and reports

- Diagnose a surprising or wrong result to root cause with real artifacts (logs, the live
  API, the actual code path) before reporting a cause. The first plausible story ("benign
  backlog", "coincidence") is not a diagnosis. Litmus: have I shown the mechanism with a
  source, or am I narrating a guess?
- Same bar for any consequential specific (a duration, a hazard, whose data): name the
  check that would falsify it; if it is cheap, run it first; if it can't be run, write
  "unverified — inferred from X" in the same sentence. A negative or coverage claim
  ("nothing uses this", "only X gets through") is checked against the real population
  first: search the workspace, run several distinct searches, or for a guard enumerate
  the real cases it must stop. Write address guards as allowlists.
- No time estimates for your own work (a build, fix, session, or package) in chat, specs,
  or plans; describe size by what it touches (files, steps, blast radius). Measured
  durations and real-world durations (travel, a game's length) are fine.
- "Is X ready / done / working?" is yes only after checking each prerequisite X's own run
  step names (installed where the runtime loads it, config, auth). Build receipts or
  passing tests are not readiness; anything unchecked is listed as "not checked: Y".
  "Check / verify X" reports what you found in plain words, not graded against a bar the
  user didn't name.
- A previously working MCP/connector tool that suddenly "isn't there": first hypothesis is
  its enable toggle was switched off (often by an update). Ask the user to re-enable it
  and retry before any deeper theory.
- Attribute every verdict, recommendation, or decision in a CHECKPOINT or decision doc:
  `user decision — YYYY-MM-DD` only for the user's explicit choice, `model recommendation
  — YYYY-MM-DD` for yours, `author unknown — documented YYYY-MM-DD` otherwise. Silence is
  not adoption.
- Talk plainly: answer first, number multi-step work, no preamble, recaps, or closers.
  Keep the closing message short (outcome first, only what the user does with it; detail
  goes in a file behind a pointer). Any code or invented term gets a plain-words gloss in
  the same breath. One copy-paste command per fenced block. Never relay tool or hook
  output that was addressed to you.

### Destructive operations and git

- Destructive ops (rm and friends) only on literal paths the user named in this
  conversation — never on paths derived from globs, find output, or variables.
- A guard that blocks a computed delete you were asked to do bans the FORM, not the
  delete: list and check the targets, then re-issue it with each path written out.
- The same bar covers bulk find-and-replace writes: every edited file individually named
  and its role known. Data artifacts (research pulls, exports, transcripts) are read-only
  evidence. No unsolicited cleanup.
- These folders aren't git repos by default, so nothing is committed or pushed unprompted.
  If you later put a project under a PRIVATE repo as its backup, a session that changed it
  commits and pushes in the same turn: a commit left local isn't a backup. New repos
  default to private; never create a repo or branch, or push to a public repo, unless
  asked. Each repo has one default branch, `main`.
- Private repos ignore only sensitive data (secrets, personal or message data) and machine
  junk (installs, caches, build output), never a file the project needs to work or resume
  (CHECKPOINT.md, CLAUDE.md, specs, docs). Harness files are ignored only in public repos.
```

### Per-project CHECKPOINT.md

```markdown
# [Project Name] Checkpoint
Last updated: [DATE UTC]   <!-- TIMESTAMP ONLY, and the "verified against reality" stamp:
                                bump it whenever a session re-reads project state. NOT a
                                change summary — that history lives in the changelog. -->

## Status
[One line: the PRESENT state only — where things stand right now. No past ("just shipped
X" → changelog), no future ("X pending / next" → Next step or Open threads). For
live-data projects, point at the live source instead of quoting numbers that go stale.]

## Goal
[1–3 lines: what this project is trying to accomplish.]

## Research
[New project or milestone: fill this first, before any implementation — prior art
(shipped solutions first), constraints, open questions, sources. Prune to one-line
findings or fold into Key decisions once the milestone ships.]

## Key decisions
[LIVE, still-contestable choices a future session would otherwise re-litigate. NOT a
rulebook and NOT an archive: a decision that hardened into a standing rule moves to
CLAUDE.md; a closed/done decision's durable record is its changelog entry — prune it,
don't keep a "Closed this session" graveyard. Litmus: still contestable AND recorded
only here?]
- (bullets)
- **Failed approaches:**
  - (what was tried and why it didn't work — the highest-value content a future
    session cannot reconstruct from files; success leaves code, failure leaves nothing)

## Open threads
- (bullets — the source of truth for incomplete work; reads like a to-do list, never a
  graveyard of done items. Every top-level bullet ends with two tags, gate then
  complexity: `[owner]` when the next action needs the user's hands or an explicit
  decision from them, else `[agent]`; then `[low]` when a smaller/cheaper model can
  finish it from the bullet alone, else `[high]`. `[blocked-by: X]` / `[gates: Y]` may
  sit before the pair; sub-bullets carry no tags. The checkpoint skill's finisher sorts
  tagged bullets into owner-low, owner-high, agent-low, agent-high order at every close
  — don't hand-sort)

## Files that matter
- `[path]` — [one-line role]

## Next step
[ONE of three declared shapes — pick what matches reality; a later session finding it
stale flips the shape rather than defending it:
  Action — one explicit, actionable sentence (only when a single workstream is live), OR
  HOLD — <what the human must decide/do>; don't <gated action> until then, OR
  Pick — Pick from Open threads (live ask outranks; then agent-side [low] to a delegated
         worker, [high] inline; owner-gated items are the owner's).
Pick is the default for non-linear projects — a stored single pointer is a strong stale
signal that future sessions will defend against the user; when several workstreams are
live at once, don't store one. This section, not Status, owns "what's next."]
```

## 4. Install core hooks

When the repository is available, use `hooks/settings-windows.example.json` or
`hooks/settings-macos-linux.example.json` as the merge source. Otherwise use the fallback
blocks below. Merge only the selected hook objects. Preserve unrelated settings and hooks.

### Windows fallback

```json
{
  "hooks": {
    "SessionStart": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "powershell.exe -NoProfile -Command \"try { if (Test-Path CHECKPOINT.md) { Write-Output '=== CHECKPOINT RECEIPT (resume context for this project) ==='; Write-Output ('CHECKPOINT.md present: ' + (Get-Item CHECKPOINT.md).Length + ' bytes / ' + @(Get-Content CHECKPOINT.md).Count + ' lines. NOT inlined here.'); Write-Output 'ACTION: Read CHECKPOINT.md to EOF before any non-pre-oriented action. If the Read shows a truncation / partial-view notice, re-Read with offset+limit until complete.'; Write-Output '=== end RECEIPT ===' } } catch { Write-Output '=== CHECKPOINT RECEIPT ERROR -- manually Read CHECKPOINT.md before acting ===' }\""
          }
        ]
      }
    ],
    "PreCompact": [
      {
        "matcher": "manual|auto",
        "hooks": [
          {
            "type": "command",
            "command": "powershell.exe -NoProfile -Command \"if (Test-Path CHECKPOINT.md) { Write-Output 'REMINDER: Context is about to be compacted. If CHECKPOINT.md in the current project has not been updated this session, rewrite it now with compressed state before proceeding.' }\""
          }
        ]
      }
    ]
  }
}
```

## 5. Install selected repository components

### Recommended orientation gate

If the repository is available:

- Windows: copy `hooks/orient_gate.ps1` to `~/.claude/hooks/orient_gate.ps1`.
- Mac/Linux: copy `hooks/orient_gate.sh` to `~/.claude/hooks/orient_gate.sh` and confirm
  `jq` exists.
- Merge the matching PreToolUse object from the repository settings example.

If only this guide is available, use Appendix A.

### Other hooks

- Windows mechanical guard: copy `hooks/guard.ps1`; merge its PreToolUse object.
- Windows security backstop: copy `hooks/deny_backstop.ps1`; read and adapt its patterns
  before enabling; merge its PreToolUse object.
- tmux/SSH receipt: copy `hooks/tmux_receipt.ps1`; enable only if the user's remote launch
  environment differs from desktop.
- Windows interview gate: copy `hooks/grill_gate.ps1`; merge its UserPromptSubmit and
  PreToolUse objects. Pairs with the `grill-me` skill; install both or neither.
- Windows `/log` reminder: copy `hooks/log_backstop.ps1`; merge its PostToolUse object
  (matcher `Skill`). Pairs with the `log` skill; install both or neither.

- Codex hooks (Windows PowerShell, only if the user runs Codex): copy the `hooks/codex/`
  folder to `~/.codex/hooks/harness/`; in its `hooks.json` replace every `<HOOKS_DIR>` with
  that folder's absolute path using forward slashes; merge the result into
  `~/.codex/hooks.json`; tell the user to open `/hooks` in Codex and trust each new hook.
  Verify with `powershell.exe -NoProfile -File <installed folder>/orient_gate_tests.ps1`
  (absolute path; expect 19/19). The gate is a reminder that records read requests, not
  proof of a read. It blocks with Codex's JSON deny form, which live `codex exec` probes on
  Codex 0.164.0-alpha.11.1 enforced; after the user trusts the hooks in `/hooks`, check it
  once by asking Codex to run a command in a project before reading its files (it should be
  blocked), and say the result in the final report.

Keep hook policies in separate matcher objects. Do not merge them into one broad matcher.

### Skills

For each selected folder under `skills/`:

1. Read its `SKILL.md` and any referenced scripts.
2. Check for a name collision at `~/.claude/skills/<name>/`.
3. If absent, copy the whole folder.
4. If present, diff it and ask before merging or replacing.
5. Verify the skill appears in a fresh session.

Do not load every skill body into the installation conversation unless needed for a
collision or verification failure.

## 6. Verify

Run every applicable check. Do not report installation complete if a selected component
has not passed its check.

1. **Manifest:** every created file exists and every merge preserved unrelated content.
2. **JSON:** user-level `~/.claude/settings.json` parses successfully.
3. **Receipt:** start a fresh session inside a project with `CHECKPOINT.md`; confirm the
   SessionStart receipt appears and its byte/line counts match the file.
4. **PreCompact:** invoke `/compact` in a test session; confirm the reminder appears.
5. **Orientation gate:** in a fresh project session, attempt one state-changing action
   before reading `CHECKPOINT.md`. Confirm it blocks, that a re-issue is still blocked
   (repository gate; one re-issue releases it under `ORIENT_GATE_BLOCK_ONCE=1` or the
   embedded fallback), and that a full Read releases it. Confirm read-only work is never blocked.
6. **Optional hooks:** run their repository tests or a safe positive/negative probe.
7. **Skills:** confirm selected skills are discoverable in a fresh session.
8. **Cross-platform warning:** the PowerShell hooks are the tested reference. Treat the
   bash port as unverified until checks 3–5 pass on the target machine.

If a check fails: diagnose the exact file, event, or matcher; fix it; rerun that check.

## 7. Finish and rollback record

Write `<workspace>/HARNESS_files_created.md` with:

1. Install date and workspace root.
2. Every file created, one absolute path per line.
3. Every existing file merged, plus a one-line description of the inserted section.
4. Selected components and verification result.
5. Rollback rule: delete only files created by this install; reverse merges manually from
   the recorded sections. Never imply that deleting a merged settings file is safe.

Final report: installed components, failed/skipped checks, and any user action still
required. Do not repeat the design rationale.

## Section 8c — Archive standard (compatibility anchor)

When `CHECKPOINT.md` exceeds 120 lines or ~30 KB, keep the newest 1–2 changelog
entries inline and move older entries byte-verbatim to
`<project>/archive/harness_changelog.md`. Use
`skills/checkpoint/archive-changelog.ps1`; the model chooses the line range and the
script moves the bytes. Never paraphrase existing changelog entries.

## Section 8d / Appendix A — Embedded orientation-gate fallback

Prefer the repository files. These blocks exist so this single file remains installable.
They are the minimal block-once form; the repository `hooks/orient_gate.ps1` / `.sh` is
stricter (a full read of the nearest CHECKPOINT.md, no re-issue pass) and checks more.

### Windows PowerShell

```powershell
# ~/.claude/hooks/orient_gate.ps1
# Blocks (exit 2) the FIRST world-changing action of a session until CHECKPOINT.md has
# been read this session, then allows (block-once). Read/Grep/Glob are never gated.
# Fails OPEN (exit 0) on any error so a gate bug can never wedge a session.
try {
    $raw = [Console]::In.ReadToEnd()
    if ([string]::IsNullOrWhiteSpace($raw)) { exit 0 }
    $j = $raw | ConvertFrom-Json
    $tool = "$($j.tool_name)"; $cwd = "$($j.cwd)"
    $tp = "$($j.transcript_path)"; $sid = "$($j.session_id)"

    $coreGated = @('Write','Edit','MultiEdit','NotebookEdit','Bash','PowerShell','WebSearch','WebFetch')
    $isGated = $false
    if ($coreGated -contains $tool) { $isGated = $true }
    elseif ($tool -like 'mcp__*') {
        $method = ($tool -split '__')[-1]
        if ($method -match '^(create|update|delete|add|send|set|fill|apply|save|submit|publish|archive|log|rebuild|respond|upload|insert|remove|patch|write|draft|move|copy)([_]|$)') { $isGated = $true }
    }
    if (-not $isGated) { exit 0 }

    # If no CHECKPOINT.md at or above cwd, nothing to orient against -> never block.
    $hasCp = $false; $dir = $cwd
    while (-not [string]::IsNullOrEmpty($dir)) {
        if (Test-Path -LiteralPath (Join-Path $dir 'CHECKPOINT.md')) { $hasCp = $true; break }
        $parent = Split-Path -LiteralPath $dir -Parent
        if ([string]::IsNullOrEmpty($parent) -or $parent -eq $dir) { break }
        $dir = $parent
    }
    if (-not $hasCp) { exit 0 }

    # Already read a CHECKPOINT.md this session?
    if (-not [string]::IsNullOrEmpty($tp) -and (Test-Path -LiteralPath $tp)) {
        if (Select-String -LiteralPath $tp -Pattern '"name":\s*"Read".*CHECKPOINT\.md' -List -ErrorAction SilentlyContinue) { exit 0 }
    }

    # Block-once: if we already nudged this session, allow (preserves the one-shot escape).
    $safeSid = ($sid -replace '[^A-Za-z0-9_-]','_')
    $flag = Join-Path $env:TEMP ("orient_gate_" + $safeSid + ".flag")
    if (Test-Path -LiteralPath $flag) { exit 0 }
    try { Set-Content -LiteralPath $flag -Value '1' -ErrorAction SilentlyContinue } catch {}
    [Console]::Error.WriteLine("ORIENTATION GATE: this session has not read CHECKPOINT.md and you are about to run a world-changing action (" + $tool + "). FIRST Read the project's CHECKPOINT.md to EOF and follow its Open threads / Next step. If you have genuinely judged this a pre-oriented one-shot, just re-issue this exact call -- the gate fires only once per session.")
    exit 2
}
catch { exit 0 }
```

### Mac/Linux bash

```bash
#!/usr/bin/env bash
# ~/.claude/hooks/orient_gate.sh — PreToolUse orientation gate (Mac/Linux).
# Mirrors orient_gate.ps1: blocks (exit 2) the FIRST world-changing action of a session
# until CHECKPOINT.md has been read this session, then allows (block-once). Fails OPEN.
raw="$(cat)"; [ -z "$raw" ] && exit 0
command -v jq >/dev/null 2>&1 || exit 0          # no jq -> fail open

tool="$(printf '%s' "$raw" | jq -r '.tool_name // empty')"
cwd="$( printf '%s' "$raw" | jq -r '.cwd // empty')"
tp="$(  printf '%s' "$raw" | jq -r '.transcript_path // empty')"
sid="$( printf '%s' "$raw" | jq -r '.session_id // empty')"

# Gate only world-changing / external tools; read-only tools pass straight through.
gated=0
case "$tool" in
  Write|Edit|MultiEdit|NotebookEdit|Bash|WebSearch|WebFetch) gated=1 ;;
  mcp__*)
    method="${tool##*__}"
    printf '%s' "$method" | grep -Eq '^(create|update|delete|add|send|set|fill|apply|save|submit|publish|archive|log|rebuild|respond|upload|insert|remove|patch|write|draft|move|copy)(_|$)' && gated=1 ;;
esac
[ "$gated" = 1 ] || exit 0

# No CHECKPOINT.md at or above cwd -> nothing to orient against -> never block.
dir="$cwd"; has_cp=0
while [ -n "$dir" ]; do
  [ -f "$dir/CHECKPOINT.md" ] && { has_cp=1; break; }
  parent="$(dirname "$dir")"; [ "$parent" = "$dir" ] && break; dir="$parent"
done
[ "$has_cp" = 1 ] || exit 0

# Already read a CHECKPOINT.md this session?
if [ -n "$tp" ] && [ -f "$tp" ]; then
  grep -Eq '"name":[[:space:]]*"Read".*CHECKPOINT\.md' "$tp" && exit 0
fi

# Block-once: per-session sentinel in the temp dir.
safe_sid="$(printf '%s' "$sid" | tr -c 'A-Za-z0-9_-' '_')"
flag="${TMPDIR:-/tmp}/orient_gate_${safe_sid}.flag"
[ -f "$flag" ] && exit 0
: > "$flag" 2>/dev/null

echo "ORIENTATION GATE: this session has not read CHECKPOINT.md and you are about to run a world-changing action ($tool). FIRST Read the project's CHECKPOINT.md to EOF and follow its Open threads / Next step. If you have genuinely judged this a pre-oriented one-shot, just re-issue this exact call -- the gate fires only once per session." >&2
exit 2
```
